# Starvis local model benchmark

Date: 2026-08-27

Hardware under test: NVIDIA GeForce RTX 3080, 10 GB VRAM. The normal deployed
profile offloads 25% of the 9B reasoning model to the GPU and keeps one Qwen
speech model in the separate Python worker.

## Executive verdict

The current collection of models is not usable as an interactive, fully local
voice assistant on this GPU. ASR and dedicated vision are individually good.
Reasoning is slow and does not reliably suppress visible chain-of-thought. TTS
is substantially slower than real time. Most importantly, ASR and TTS share one
model slot, so every spoken turn pays a large model-switch penalty.

| Function | Model and deployment | Result | Verdict |
|---|---|---:|---|
| Reasoning | Qwen3.8 9B Distill Q5_K_M, 25% GPU | 1.03 s TTFT, 9.99 tok/s | Limited |
| Tool selection | Same reasoning model | Correct call in 8.61 s | Usable for background actions |
| Speech recognition | Qwen3-ASR 1.7B on CUDA | 2.47 s for 11.6 s audio, WER 0.00 | Usable while resident |
| Speech synthesis | Qwen3-TTS 1.7B Dylan on CUDA | 40-46 s for 12-14 s audio | Not interactive |
| Vision, deployed | Text-only `starvis-local` alias | HTTP 400 on image input | Broken |
| Vision, dedicated | Qwen3-VL 8B Q4_K_M on CUDA | 0.77 s camera analysis | Usable while resident |

## Measurements

### Reasoning provider

- Time to first token: 1.031 seconds.
- Generation rate: 9.99 tokens/second with the model only partly offloaded.
- A 256-token arithmetic/JSON request took 26.653 seconds.
- The arithmetic result was correct, but the model used all 256 tokens exposing
  `Thinking Process` and never produced the requested JSON-only final answer.
- `chat_template_kwargs.enable_thinking=false` and `/no_think` did not suppress
  this behavior for the downloaded distilled GGUF.
- A production-style `get_station_status` function request selected the correct
  tool and arguments in 8.61 seconds. A complete tool loop requires another
  model pass after the tool result, so practical action latency is higher.

Conclusion: adequate for asynchronous summaries and simple tool selection, but
not reliable or fast enough for a polished conversational assistant.

### Speech recognizer

- Test audio: 11.6 seconds of known French speech generated by Dylan.
- Warm transcription: 2.473 seconds, real-time factor 0.213.
- Word error rate on the synthetic sample: 0.00.
- Switching from resident TTS to ASR: 31.085 seconds total.

Conclusion: the ASR model itself is usable. The current shared-worker model
swap is not. The zero synthetic WER is an optimistic result and still needs a
small corpus of real microphone recordings, noise, and Quebec French accents.

### Speech synthesizer

- Warm long synthesis: 40.243 and 46.145 seconds.
- Generated audio duration: 11.6 and 13.52 seconds.
- Real-time factor: 3.47 and 3.41; generation is over three times slower than
  playback and cannot stream speech as it is produced.
- Exact short preview, `Bonjour, voici ma voix.`: 7.329 seconds for 1.76 seconds
  of audio, real-time factor 4.16.
- Switching back from ASR to TTS: 50.509 seconds.
- The runtime warns that `flash-attn` is unavailable and uses manual PyTorch,
  but the measured gap is too large to treat this as an interactive engine.

Conclusion: voice quality may be acceptable, but this implementation is not
usable for previews, briefings, or dialogue where the user waits for speech.

### Vision analyzer

The deployed `starvis-local` alias is the 9B text model and explicitly reports
`vision: false`; QtPanel nevertheless routes local image analysis to it. The
benchmark correctly received HTTP 400, matching the sentry log entries that say
analysis was unavailable.

The installed Qwen3-VL 8B model was then tested in an isolated llama.cpp server:

- Cold server load: 53.87 seconds.
- First synthetic image request: 3.984 seconds.
- Cache-busted warm request: 0.657 seconds.
- Real camera frame: 0.767 seconds.
- Camera result was correct: one person, two vehicles, daylight, with a useful
  security-oriented scene summary.
- Small synthetic text OCR was imperfect (`STARVIS 42` became `STARS8 42`), so
  this model should not be trusted for license plates or exact small text.

Conclusion: Qwen3-VL 8B is fast and useful for event-triggered camera triage if
it remains resident. It is currently not wired to the deployed vision route.

## End-to-end impact

The measured synthetic local voice turn is approximately:

`2.473 s warm ASR + 26.653 s reasoning + 50.509 s TTS reload/generation = 79.635 s`

Even a short preview takes 7.329 seconds. A normal assistant turn near 80
seconds is not viable. Cold startup after filesystem caching makes the core
services reachable in 22.561 seconds and prewarms TTS in 28.464 seconds. The
health endpoint now remains responsive while prewarm is in progress.

Normal reasoning plus resident TTS used about 8.3-8.9 GB VRAM. Dedicated vision
used about 7.7 GB. The RTX 3080 cannot keep the current reasoning, TTS, ASR, and
vision models resident together, so orchestration alone cannot remove all swap
latency.

## Recommended architecture

1. Keep Qwen3-VL 8B as a dedicated, event-driven vision service, but make its
   residency policy explicit. It cannot coexist with the current full stack on
   10 GB VRAM.
2. Keep Qwen3-ASR only if it can run in a separate resident process within the
   final memory budget. Otherwise benchmark a smaller real-time ASR engine.
3. Replace Qwen3-TTS 1.7B for interactive speech with a CPU-capable streaming
   TTS engine that achieves real-time factor below 0.5. Preserve Qwen TTS only
   as an optional high-quality offline renderer if desired.
4. Replace the distilled reasoning GGUF with an instruct/tool model that obeys
   non-thinking mode and structured output. Target at least 20 tok/s and verify
   complete tool loops, not only tool selection.
5. Separate provider endpoints in QtPanel: reasoning, vision, ASR, and TTS must
   have independent readiness and model identities. Never infer vision support
   from reasoning endpoint health.
6. Add this benchmark to the settings diagnostics page and block a provider
   from showing `Ready` when its functional probe fails.

Raw timings, outputs, transcripts, GPU snapshots, and vision results are stored
in `benchmark.json`, `reasoning-tool.json`, `tts-preview.json`, and
`vision-dedicated.json` beside this report.
